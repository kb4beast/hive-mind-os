# Implementation Program

## Outcome

Deliver a repository-neutral local knowledge product that can:

- preserve every material consideration and lifecycle transition in protected,
  append-only canonical state;
- show a complete private Obsidian-compatible graph without making Obsidian
  authoritative;
- let one stable idea traverse any number of immutable passes and explain every
  return through the workflow;
- trace all specialist roles, temporary court identities, gates, work, deliverables,
  outcomes, lessons, champions, and challengers; and
- create independently judged, structurally allowlisted learning abstractions in a
  local shared registry without revealing repository secrets, IP, proprietary
  expression, customer data, private identifiers, or incompatible-license content.

The first program stops at a qualified **local** registry and read-only prior-art
lookup. Remote/public publication, persistent watch mode, bidirectional Obsidian
Inbox, external embeddings, and automatic shared-lesson activation are not authorized.

## Truthful starting state

- Planning baseline: current `main` at

- Program plan: 31 nodes, 18 compiled rounds, zero implementation nodes started.
- Existing reusable code: append-only kernel events, bounded memory, court records,
  lessons, challenger evaluation, promotion, rollback, and JSON/HTML operational views.
- Missing on current `main`: stable `Idea`/`IdeaPass`, complete knowledge-edge model,
  private Obsidian projector, shared release gateway, sanitized registry, and the
  end-to-end integration among those parts.
- The Phase 3 branch at `2cbfe1d` is prior-art evidence, not current product code. Its
  projection mechanics may be adapted only after current-contract verification; it
  must not be merged wholesale.

Program implementation is therefore **0/31 nodes (0%)**. Existing foundation code is
credited as required input and risk reduction, not as completion of a new node whose
acceptance contract has never run.

## Delivery groups

Nodes: `BASELINE-000`, `SOURCE-010`, `AUTHORITY-020`, `LEARNING-030`,
`SCAFFOLD-040`.

This group seals point-in-time truth, identifies the canonical-store problem, closes
authority expansion, makes imported lessons inert, and establishes one owner for shared

### Group B — Contracts before implementation

`PROJECT-CONTRACT-130`, `RELEASE-CONTRACT-140`, `ADVERSARY-150`,
`OBSIDIAN-SOURCE-160`, `RETENTION-170`.

This group defines:

- classification, proprietary/PII/license/provenance/publishability rules;
- current, retained official-source evidence for every named Obsidian compatibility
  claim;
- append-only metadata separated from erasable protected bodies, with deletion and
  takedown receipts;
- projection transactions and offline release bundles; and
- a synthetic adversarial disclosure and poisoning corpus.

### Group C — Canonical private knowledge runtime

Nodes: `STORE-200`, `IDEA-RUNTIME-210`, `GRAPH-ADAPTERS-220`,
`PRIVATE-PROJECTOR-230`, `RELEASE-CANDIDATE-240`.

This group establishes the durable event boundary, repeated idea behavior, complete
role/court/work/delivery/learning adapters, a one-shot external private projector, and
newly composed release candidates. It does not write a shared registry.

### Group D — Human graph and safe local sharing

Nodes: `OBSIDIAN-VIEWS-300`, `TRACE-310`, `RELEASE-GATE-320`,
`SHARED-REGISTRY-330`, `CLI-340`.

This group renders the graph and all arrows, explains every workflow return, independently
gates offline bundles, admits approved abstractions into a local content-addressed
registry, and exposes bounded commands. Obsidian remains optional and read-only.

### Group E — Learning, isolation, migration, and demo surfaces

Nodes: `PRIOR-ART-400`, `FEDERATION-410`, `MIGRATION-420`, `DASHBOARDS-430`.

This group makes safe records available as read-only prior art, proves tenant and

legible for audiences from beginner to expert.

### Group F — Exact-candidate judgment and handoff

Nodes: `QUALIFY-500`, `RELEASE-COURT-510`, `HANDOFF-520`.

This group runs end-to-end adversarial qualification, convenes a distinct release
Judge, and delivers a bounded local product with residual obligations and rollback.

## Record-type transformations

Records do not mutate from one type into another. A transition appends a new record and
a typed edge:

```text
Source -> AtomicClaim -> IdeaEncounter -> Idea -> IdeaPass
IdeaPass --adopt/adapt--> WorkItem -> Candidate -> VerifiedDeliverable
VerifiedDeliverable -> Delivery -> Outcome -> LearningSignal -> Lesson
Lesson -> Challenger -> Evaluation -> Promotion or Rejection or Rollback
Outcome/Incident/Appeal/Remand -> ReentryEvent -> later IdeaPass
Approved abstraction -> SharedLearningCandidate -> ReleaseDecision -> SharedLearning
```

An idea may repeat the loop indefinitely. Chronology and execution dependencies always
move forward; a semantic backward arrow points from the new remand/re-entry fact to the
earlier stage it requests and to the later pass that fulfills it.

## Role ownership

| Role | Program responsibility |
| --- | --- |
| Orchestrator | Outcome, decomposition, budgets, dependencies, round scheduling, return reasons, stopping, release handoff |
| Explorer | Source inventory, idea encounters, collision evidence, prior-art lookup, problem selection |
| Architect | Identity, schemas, invariants, threats, migrations, rollback, release contract |
| Builder | Isolated store/runtime/projector/gateway/CLI implementation and focused tests |
| Curator | Independent correctness, provenance, privacy/IP/license, adversarial leakage evidence, release court exhibits |
| Integrator | Repository/tenant contracts, projection, local registry, federation, CLI surfaces, single integration transaction |
| Steward | Durability, replay, drift/conflicts, backup/restore, migration, tombstones, health |
| Optimizer | Lesson admission, champion/challenger linkage, held-out outcomes, prior-art evaluation |

Temporary identities remain separate: Clerk preserves the case; Advocate argues for the
claim; Cross-Examiner attacks it; Expert Witness supplies domain testimony; Judge issues
the disposition; Appeals Judge reviews a later appeal. A graph node showing a role does
not prove that role executed; every node carries an evidence-maturity label.

## What writes where

```text
all roles/tools/courts
        |
        v
protected canonical store (authority; outside shared/public repository)
        |
        +--> private projector authority
        |         |
        |         v
        |    private generated Obsidian-compatible vault
        |    all permitted summaries, roles, courts, passes, arrows, receipts
        |
        +--> release-candidate builder (separate authority)
                  |
                  v
             offline fail-closed release court
                  |
                  v
             local sanitized shared registry
             approved abstractions only
```

No role writes directly to generated notes. Raw secrets, credentials, hidden reasoning,
raw transcripts, unbounded logs/tool bodies, and protected source expression are not
materialized even in the private vault. Proprietary repository summaries may remain in
the access-controlled private plane when policy permits; they never cross into the
shared record. The shared registry contains only a newly composed allowlist of abstract
mechanism, applicability, constraints, evaluated outcome status, counterexamples,
uncertainty, expiry, and non-reversible evidence digests.

## Milestones and stop conditions

1. **M1: trustworthy contracts** — Groups A and B pass. Stop if canonical ownership,
   authority, classification, license/provenance, or idea-pass identity is ambiguous.
2. **M2: private MVP** — Group C plus private projection/trace from Group D passes.
   This is the first useful product checkpoint; no shared release is required.
3. **M3: local safe-learning laboratory** — offline gate and local registry pass every
   adversarial fixture. Stop if any known private/IP/secret bypass succeeds.
4. **M4: measured reuse** — prior-art evaluation reports duplicate escape, false merge,
   poisoning, and outcome evidence. Do not claim improvement from activity counts.
5. **M5: qualified local release** — exact-candidate Curator evidence and distinct Judge
   disposition exist. Full CI remains green and rollback is demonstrated.

## Work estimate without false precision

The plan intentionally avoids calendar promises unsupported by throughput evidence.
Its measurable size is:

- 31 independently reviewable node contracts;
- 18 integration rounds;
- 6 delivery groups;
- 5 serial safety/release milestones; and
- one full exact-candidate qualification and one independent release court.

After two completed rounds, the Orchestrator can use observed cycle time, remand rate,
and validation cost to estimate remaining calendar time. Before that evidence exists,
any week estimate is a planning hypothesis rather than a commitment.
