## Direct Git-engine and repository-boundary controls

The independent qualification caller pinned this native executable rather than a
`cmd.exe` shim or `PATH` lookup:

The verifier rejects every inherited environment-variable name beginning `GIT_`
case-insensitively before invoking Git. It requires the caller's canonical absolute
path and expected digest and, on Windows, a `.exe` suffix. This implements the exact
recorded Windows boundary but fails the intended native-file requirement on POSIX,
where it checks only executable permission and therefore accepts script wrappers.
It ignores inherited `PATH`, resolves the real Git directory, linked-worktree
`commondir`, and index, and rejects object alternates.
Each child receives a minimal environment with explicit `--git-dir` and
`--work-tree`, disabled system/global config, replacement objects, prompting,
external diff/textconv, optional locks, and risky local configuration overrides.

The verifier opens the Git executable, retains the handle, and checks canonical
path/open-file identity plus retained-handle and current-path full SHA-256 before
and after every invocation. Git runs without a shell under a neutral working
directory. Stdout/stderr are incrementally bounded to 16 MiB; timeout, kill,
nonzero, and non-UTF-8 outcomes are typed failures. Candidate-controlled files,
Git pointer files, and the index have explicit read limits. The manifest has exact
top-level and section schemas and is scanned for executable command authority.

The proof compares raw HEAD blobs, stage-zero index entries, and direct worktree
bytes; validates every tracked path, mode, blob, visibility flag, untracked and

   transparent executable shell wrapper with a caller-pinned wrapper digest can
   delegate the full argument list to Git. This contradicts the direct-native-
   executable contract and requires an implementation correction plus negative
   tests in an append-only successor.
2. Hashing `git.exe` does not bind its dynamic loader, DLLs, `libexec` helpers,
   operating-system runtime, or filesystem implementation. Those dependencies need
   a stronger externally frozen execution host before execution qualification.
3. Portable pathname and retained-handle checks detect but cannot eliminate every
   hostile same-SID swap-and-restore or equivalent TOCTOU attack. Qualification for
   execution needs read-only media or independently enforced custody/isolation.
4. The one-shot verifier API and its retained executable handle are content-
   qualification controls, not a general reusable security boundary.
5. The inherited `plan.json` does not itself enumerate the new caller-pinned Git
   executable path/digest, frozen Git runtime bundle, or external minimum-version/
   revocation-policy digest. ADR-069 and the manifest add those Envelope-B/runtime
   obligations, but activation must remain deferred until one authoritative runtime
   contract consistently carries and enforces them. The plan alone is not claimed
   to carry the complete V3 Git-boundary activation contract.
6. No independently retained raw transcript or transcript digest exists for the
   committed-verifier JSON, focused-suite output, or prescribed full-gate output.
   This report supports the recorded commands and terminal summaries, not raw-
   transcript integrity or independent transcript replay. Later full tests made
   `C:\h3-a47e9798` ignored-dirty, so it cannot be reused for another pristine

7. The same Windows SID cannot establish distinct-principal trust. Activation needs

8. Activation additionally requires an authenticated minimum-version/revocation
   policy, fresh short capability and lease, exact interpreter/runtime binding,
   pristine external host, independent receipts, one-run nonce/deadline/ledger,
   rollback, and revocation.
9. `SRC-024` remains `QUARANTINE_CONTENT_UNREAD`; `SRC-025` remains unresolved.

10. The Hardened Vision Contract/runtime-reference conflict remains deferred. No

11. Capability never expands authority. The owner's directive authorizes this
